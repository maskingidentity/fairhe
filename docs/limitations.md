# Assumptions and limitations

How the implementation stands against the assumptions of the paper (Table 7
of the full version), and what else limits it. "Met" means the prototype
implements what the assumption names; "stand-in" means a substitute that a
deployment must replace; "not met" means the prototype does not provide it.

## Assumptions

| Assumption | Prototype | Status |
|---|---|---|
| NIZK zero knowledge | Groth16 (gnark v0.15.0) with one BSB22 commitment per circuit | Met, as gnark implements it |
| NIZK simulation extractability | Groth16 is not simulation extractable; proofs are bound to their statements (order ID and digests are public inputs) | Not met by the deployed circuits; option O2 adds straight-line extraction of the witness (in-circuit encryption under a setup key) to pi_member at +2.8% (BFV) and +3.1% (CKKS) constraints; `docs/results/tab_v8_se.tex` lists estimates for the other proofs |
| CRS generated by neither its prover nor its verifier | `cmd/keys` runs a local Groth16 setup | Stand-in for the market-wide ceremony of Setup (i) |
| Commitment hiding and binding | Salted Poseidon2 hash commitments with 128-bit salts (`hashes.Commit`) | Met in the random-oracle model |
| Decision RLWE | N = 2^13, ternary secrets, errors in [-19, 19], chains of `pkg/rlwe/flagship.go` | Met; the lattice estimator (commit 53da598, core-SVP) gives 186.9, 263.7, 204.9 and 239.4 bits on the actual chains (test G1) |
| Circular security of evaluation keys | The running example needs no evaluation keys | Not used |
| Public coins from H_coin | SHA-256 seed expanded by Lattigo's KeyedPRNG (BLAKE2b XOF), pinned by known-answer tests | Met in the random-oracle model; the expansion is tied to Lattigo v6.1.1 |
| Salted digests h_s (Case 2) and h_sB (Case 1) | Poseidon2 over the packed secret and a 128-bit salt | Met in the random-oracle model |
| Flooding width | sigma_fl = 79, 73, 70, 82 from the worst-case bounds, checked in code; uniform flood on the closed interval | Met; the samplers are not constant-time |
| Decoding headroom of the BFV modulus | `Params.CheckMargins` checks the decoding conditions and the margins of Appendix C.4 | Met |
| One form (Case 1), one circuit and key set (Case 2) per class | One verification key per circuit, class and parameter set; the function is a witness | Met |
| Collision resistance of H_dig | Poseidon2, width 2, 6 full and 50 partial rounds (gnark-crypto defaults) | Assumed |
| Blob link | EIP-4844 KZG via go-ethereum's kzg4844 (Ethereum ceremony setup), versioned hash, z = keccak256(tag, vh, h_D) mod r_bls, point-evaluation precompile | Met on the simulated chain |
| Ledger: total order, inclusion within delta, contract rules | go-ethereum simulated backend: one node, every transaction mined in the next block | Stand-in; inclusion delays, fee markets and censorship are not modelled |
| Blob retention W | The simulated backend has no blob retrieval; `market.BlobNet` keeps the blobs of included transactions and serves each for W blocks after its inclusion | Stand-in |

## Other limitations

- Time is measured in block numbers (delta = 32 blocks, T_max = 7200 blocks),
  and every transaction is mined at once, so the timing rules are exercised
  but not under realistic inclusion delays.
- The data-availability layer is a local store addressed by the ledger's
  digests; a missing value ends the exchange in a reject or no order, as the
  paper specifies, but no availability protocol is implemented. Option O6
  replaces it by blob data (`market.BlobBoard`), whose availability for W the
  network provides; a value posted as blobs expires after W, so long-lived
  offers and keys must be posted again.
- The archive of option O7 is a local directory, one file per versioned
  hash. It is trusted for availability only (readers check against the
  versioned hash) and must sync within W of each claim.
- Off-chain proofs take the polynomials as public inputs: about 16,000 to
  25,000 public inputs each, which the counterparty supplies from values it
  fetched and checked against their digests.
- Measurements ran on one machine (Windows, 32 GB RAM, commit limit
  37.6 GiB); full-scale proving of the Case 1 evaluation proof needs about
  10 GiB of commit and a proving key of several GiB.
- The measured function class is of degree one in the encrypted operand.
- Option O1 (settlement for chains that cannot verify proofs) is implemented
  at the circuit level: pi_seal (`pkg/zk/sealv8`) and the sealed correctness
  proofs are measured at full scale (`docs/results/tab_v8_o1.tex`). Its
  settlement messages (adaptor signatures, `pkg/adaptor`) are not run end to
  end.
- Test IDs are listed in `docs/tests.md`.
